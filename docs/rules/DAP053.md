# DAP053

Runtime type-handlers under native AOT

`[module: UseRuntimeTypeHandlers]` tells generated code to defer to Dapper's own decision
procedure when it executes, so that handlers registered with `SqlMapper.AddTypeHandler` are
honored. That is a useful migration mode on a JIT runtime - and a trap when publishing native
AOT, which is why this warns only when `PublishAot` is set.

What it defers to is `SqlMapper.LookupDbType` and, on the read side, vanilla's handler
machinery - including `SqlMapper.TypeHandlerCache<T>`, a generic type instantiated over a type
chosen at runtime. ILC cannot see which instantiations to keep, and nothing warns at publish
time; the failure arrives on the deployed app as:

```
'Dapper.SqlMapper+TypeHandlerCache`1[System.Guid]' is missing native code or metadata
```

**The fix**: declare the handlers, so the generator bakes the dispatch and ILC keeps the handler
because generated code genuinely constructs it:

``` csharp
[module: TypeHandler(typeof(LocalDate), typeof(LocalDateHandler))]
```

then drop `[UseRuntimeTypeHandlers]` (or spell it `[module: UseRuntimeTypeHandlers(false)]`
while migrating a large codebase, to keep the two modes visible in the diff).

An existing handler written against vanilla Dapper can be declared as-is - generated code adapts
it - so migrating is usually a matter of moving the registration from a startup method to an
attribute, not rewriting the handler.
